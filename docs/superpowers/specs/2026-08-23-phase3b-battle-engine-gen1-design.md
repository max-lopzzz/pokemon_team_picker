# Phase 3b: Battle Engine (Gen 1) — Design

## Context

This is the fourth phase of the `pokemon_team_picker` rewrite (see
[Phase 1's spec](2026-08-23-phase1-web-foundation-design.md) for the phase
breakdown, [Phase 3a's spec](2026-08-23-phase3a-battle-engine-gen6-9-design.md)
for the Gen 6-9 battle engine this phase parallels). Phase 3a explicitly
scoped Gen 1 out as a separate phase because Gen 1's mechanics are
genuinely different, not just a variant: no Special Attack/Special Defense
split, no natures (they didn't exist until Gen 3), a completely different
critical-hit mechanic, its own type chart (including two well-known bugs),
and no minimum-damage guarantee.

This spec covers Gen 1 (Red/Blue/Green/Yellow) specifically.

## Decisions carried from discussion

- **IV/EV/DV reconciliation**: `roster.db` stores modern IVs (0-31), EVs
  (0-252), and a nature — collected uniformly regardless of which game was
  selected, per Phase 2's design. Gen 1 has no such system (DVs 0-15, Stat
  Experience 0-65535, no natures). Rather than reopening Phase 2's data
  model, this phase **reinterprets** the roster's stored numbers:
  - DV = `clamp(round(IV / 2), 0, 15)`
  - Stat Experience = `clamp(round((EV / 252) × 65535), 0, 65535)`
  - Nature is ignored entirely (Gen 1 has no nature mechanic).
  This is an approximation, not authentic Gen 1 data entry — documented as
  such, not hidden.
- **Critical hits are modeled** (unlike Phase 3a, which excluded them).
  Gen 1's crit chance is Speed-based and can exceed 25% for fast Pokémon
  (up to ~99.6% for high-crit-ratio moves), and a crit changes the
  *level* term used throughout the whole damage formula, not just a late
  flat multiplier — too significant to omit for this era.
- **Type chart**: generated by deriving from the already-verified modern
  `typeChart.ts` (drop Dark/Steel/Fairy, apply 5 documented historical
  deviations), not a fresh hand-transcription — see "Type chart" below for
  the exact overrides and their provenance.
- **Species types**: some species (Clefairy, Jigglypuff, Mr. Mime, and a
  handful of others) were retroactively given the Fairy type in Gen 6,
  which didn't exist in Gen 1. This phase resolves a species' Gen 1 type
  from PokeAPI's `past_types` field (filtered to `generation-i`) when
  present, falling back to the current type otherwise.

## Type chart

`gen1TypeChart.ts` is generated by a script that:
1. Loads the already-generated, already-verified `typeChart.ts` data (the
   Gen 6-9 chart, itself generated from `typechart.csv` in Phase 3a).
2. Drops the `dark`, `steel`, and `fairy` rows and columns, leaving the 15
   types that existed in Gen 1.
3. Applies 5 explicit overrides, documented here with their basis (general
   Pokémon-community historical knowledge — Bulbapedia's own page-scraping
   via automated tooling proved unreliable for this specific table during
   this phase's research and contradicted itself across two fetch
   attempts on the same page, so these are asserted from well-established
   general knowledge rather than a freshly re-verified source):
   - `ghost → psychic`: `0` (not `2`) — the well-known Gen 1 bug where
     Ghost-type moves have no effect on Psychic-type Pokémon.
   - `ghost → ghost`: `0` (not `2`) — a related Gen 1 quirk.
   - `bug → poison`: `2` (not `0.5`)
   - `poison → bug`: `2` (not `1`)
   - `ice → fire`: `1` (not `0.5`) — Ice-type moves were neutral against
     Fire-type Pokémon in Gen 1 only, becoming not-very-effective from
     Gen 2 onward. (Corrected during Task 2's implementation: the
     original research for this spec mistakenly attributed this
     deviation to `ice → poison`, which has no Gen 1-specific change at
     all — caught and independently re-verified during the Phase 3b
     implementation's task review.)

This keeps the same "generate from a base, don't hand-type a large table"
discipline Phase 3a established, while being explicit that the override
list itself — unlike Phase 3a's CSV-sourced chart — could not be
independently re-verified against a second reliable source during this
phase's research, and is worth a spot-check against a physical Gen 1
cartridge or a trusted community reference before this ships if extra
confidence is wanted.

## New modules

All in `web/src/core/`, prefixed `gen1` to distinguish from Phase 3a's
modules (which stay unchanged and continue serving Gen 6-9):

- **`gen1TypeChart.ts`** — generated as described above.
  `getGen1TypeEffectiveness(attackingType, defendingType): number`.
- **`gen1Types.ts`** — `getGen1Types(species): Promise<string[] | null>`,
  a small PokeAPI-backed lookup (built on `apiCache.ts`'s `fetchCached`,
  same pattern as every other client) that reads `past_types`, filters
  for the entry whose `generation.name === "generation-i"`, and returns
  that entry's types; falls back to the species' current types (via the
  same `/pokemon/{slug}` payload) if no Gen 1-specific entry exists. Kept
  separate from Phase 1's `getSpeciesInfo` rather than extending it —
  `SpeciesInfo` is already used by Phase 1's shipped pages and Phase 3a's
  matchup engine; this avoids rippling a Gen 1-specific concern into
  code those already rely on.
- **`gen1Stats.ts`** — pure stat calculator implementing the real Gen 1/2
  formula:
  ```
  HP    = floor(((Base+DV)×2 + floor(ceil(sqrt(StatExp))/4)) × Level/100) + Level + 10
  Other = floor(((Base+DV)×2 + floor(ceil(sqrt(StatExp))/4)) × Level/100) + 5
  ```
  `calculateGen1Stats(base: StatBlock, dvs: StatBlock, statExp: StatBlock, level: number): StatBlock`.
  No nature parameter — Gen 1 has none. The single "Special" stat is
  represented by using the species' base Special Attack (`spa`) value for
  both `spa` and `spd` in the input `base: StatBlock` the caller passes in
  — historically accurate, since Gen 2's stat split set the new Special
  Defense equal to the old Special stat for every pre-existing species.
- **`gen1Crit.ts`** — `getGen1CritChance(baseSpeed: number, highCritRate: boolean): number`,
  implementing `threshold = highCritRate ? min(floor(baseSpeed/2) × 8, 255) : floor(baseSpeed/2)`,
  returning `threshold / 256`.
- **`gen1Damage.ts`** — the Gen 1 damage formula, structurally close to
  Phase 3a's but with the crit multiplier folded into the level term and
  **no minimum-damage floor** (Gen 1 can genuinely compute 0 damage — the
  game calls this "the move missed," not a guaranteed-1-HP hit; this
  engine represents it the same way an immune matchup is represented —
  `{min: 0, max: 0}` — since the practical downstream meaning, "this
  attack cannot progress the battle," is the same regardless of which
  rule produced it).
  `calculateGen1DamageRange(attackerLevel, attackerStats, defenderStats, move, attackerTypes, defenderTypes, critical: boolean): DamageRange | null`.
- **`gen1Matchup.ts`** — the orchestrator, parallel to Phase 3a's
  `matchup.ts` but Gen 1-flavored. Reuses Phase 1's `getSpeciesInfo` only
  for abilities/sprite (not types — types come from `gen1Types.ts`), and
  Phase 3a's `getBaseStats`/`getMoveData` unchanged. **Known approximation:**
  base stats and move types/power are taken from PokeAPI's current values,
  not era-adjusted — several Gen 1 species received base-stat buffs in
  Gen VI (e.g. Butterfree's Special Attack 80→90), and a few moves changed
  type after Gen 1 (e.g. Bite Normal→Dark). PokeAPI's `/move` endpoint
  exposes a parallel `past_values` field for this, mirroring `past_types`,
  but wiring it up is out of scope for this phase — flagged here rather
  than asserted away. Returns both a non-crit result and a crit result.

## `MoveData` extension

`getGen1CritChance` needs to know whether a move has a high critical-hit
ratio (Slash, Razor Leaf, Karate Chop, etc.) — PokeAPI exposes this as
`move.meta.crit_rate` (0 = normal, >0 = high). Rather than a new client,
this is one additive field on the existing, shared `MoveData` type and one
extra line in `moveData.ts`'s existing `parse` callback:

```ts
export interface MoveData {
  name: string;
  type: string;
  category: "physical" | "special" | "status";
  power: number | null;
  priority: number;
  highCritRate: boolean; // new
}
```

This is exactly the kind of small, safe extension the `apiCache.ts`
refactor was meant to make cheap — Phase 3a's `matchup.ts` and `damage.ts`
simply ignore the new field.

## Data flow

```ts
export interface Gen1MatchupAttacker {
  species: string;
  level: number;
  ivs: StatBlock; // reinterpreted as DVs
  evs: StatBlock; // reinterpreted as Stat Experience
}

export interface Gen1MatchupDefender {
  species: string;
  level: number;
  // no dynamax field — Dynamax doesn't exist in Gen 1
}

export interface Gen1MatchupInput {
  attacker: Gen1MatchupAttacker;
  attackerMove: string;
  defender: Gen1MatchupDefender;
}

export interface Gen1MatchupOutcome {
  damageRange: { min: number; max: number };
  hitsToKO: { min: number; max: number };
}

export interface Gen1MatchupResult {
  normal: Gen1MatchupOutcome;
  criticalHit: { chance: number } & Gen1MatchupOutcome;
  moveOrder: "attacker" | "defender" | "tie";
}

function evaluateGen1Matchup(input: Gen1MatchupInput): Promise<Gen1MatchupResult | null>;
```

`evaluateGen1Matchup`:
1. Fetches (in parallel): `gen1Types.ts` for both Pokémon, `getBaseStats`
   for both, `getMoveData` for the move.
2. Returns `null` if any lookup fails, or the move is a status move — same
   graceful-degradation contract as Phase 3a.
3. Converts the attacker's roster IVs/EVs to DVs/Stat Experience per the
   reinterpretation above. The defender (a trainer's Pokémon, with no
   roster data — `gym_leaders.db` has no per-Pokémon stat data, same as
   Phase 3a) uses `DV 15, Stat Experience 0` directly — the Gen 1-native
   equivalent of Phase 3a's own trainer convention ("perfect IVs, 0
   EVs"), not derived from any reinterpretation, since there's no stored
   roster value to reinterpret for a trainer Pokémon in the first place.
4. Computes both Pokémon's stats via `gen1Stats.ts`.
5. Computes the crit chance via `gen1Crit.ts` from the **attacker's**
   base Speed (crit chance depends on the attacking Pokémon, not the
   defender) and the move's `highCritRate`.
6. Computes both a normal (`critical: false`) and a critical
   (`critical: true`) damage range via `gen1Damage.ts`, each with their
   own `hitsToKO`.
7. Computes move order the same way Phase 3a's `matchup.ts` does (move
   priority, falling through to a Speed comparison, `"tie"` on an exact
   tie) — Gen 1's priority moves (e.g. Quick Attack) use the same
   `MoveData.priority` field already fetched, no new logic needed.

## Error handling

Same graceful-degradation contract as Phase 3a: any failed lookup, an
unrecognized move category, or a status move → `null`, never a throw.
`gen1Types.ts` additionally falls back to current types (rather than
returning `null`) when a species has no Gen 1-specific `past_types` entry
— which is the common case; only a handful of species need the override.

## Testing

- `gen1TypeChart.ts`: generated-file test mirroring Phase 3a's — spot-check
  the 5 overrides plus several unchanged values, confirm 15×15 = 225 total
  pairs (not 18×18).
- `gen1Stats.ts`: TDD with hand-computed reference values (DV/StatExp
  worked by hand, same rigor as Phase 3a's `stats.ts`).
- `gen1Crit.ts`: TDD, hand-computed threshold/chance for a few base Speed
  values, both with and without `highCritRate`.
- `gen1Damage.ts`: TDD with hand-computed reference values for both a
  normal and a critical hit, plus a case confirming `{min: 0, max: 0}` is
  reachable (no floor) where Phase 3a's equivalent case would have been
  clamped to 1.
- `gen1Types.ts`: mocked-`fetch` tests (same pattern as every other
  PokeAPI client) covering the `past_types`-present case and the
  fallback-to-current-types case.
- `gen1Matchup.ts`: orchestrator test with all fetch-backed dependencies
  mocked, plus one exact hand-verified full-chain result (mirroring Phase
  3a's `matchup.test.ts` first test).

## Out of scope (deferred)

- Gen 2-3 and Gen 4-5 mechanics (Phases 3c/3d).
- Authentic DV/Stat-Experience entry in the roster UI (the reinterpretation
  above is an accepted approximation).
- Status conditions, weather, held items (same as Phase 3a — no data
  exists for any of this).
- Any UI/route integration — this phase, like 3a, is a pure library
  consumed by Phase 4.
